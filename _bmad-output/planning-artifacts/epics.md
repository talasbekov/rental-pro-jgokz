# rental-pro-jgokz - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for rental-pro-jgokz (ЖильеGO), decomposing the requirements from the PRD, UX Design, and Architecture into implementable stories.

## Requirements Inventory

### Functional Requirements

**Поиск и подбор квартир (FR1-FR12):**
- FR1: Гость может описать потребность в квартире на естественном языке через Telegram-бот
- FR2: Система извлекает параметры из запроса (город, даты, бюджет, комнаты, локация, кол-во гостей, время заезда) на русском языке (MVP). [Growth] Поддержка казахского и английского языков
- FR3: Бот уточняет недостающие параметры через диалог
- FR4: Гость может отправить геолокацию для сортировки квартир по расстоянию
- FR5: Система выдаёт только квартиры, свободные на запрашиваемые даты
- FR6: Гость видит карточки квартир (фото, описание, рейтинг, цена, расстояние, статус проверки)
- FR7: Гость может листать варианты последовательно
- FR8: Гость может использовать structured flow (кнопки/меню) как альтернативу NLP
- FR9: Гость использует бота на русском языке (MVP). [Growth] Поддержка казахского и английского языков
- FR10: В ночном режиме (22:00-06:00) система фильтрует только квартиры с мгновенным доступом (smart-замок) в радиусе 3 км от геолокации гостя
- FR11: Гость может добавить квартиру в избранное
- FR12: Гость может просмотреть полную информацию о квартире (все фото, описание, отзывы, правила)

**Бронирование и оплата (FR13-FR24):**
- FR13: Гость может забронировать выбранную квартиру
- FR14: При начале оплаты квартира блокируется на 10 минут (booking hold)
- FR15: Гость может оплатить через Kaspi-перевод (копирование реквизитов + загрузка скрина)
- FR16: Оператор верифицирует скриншот Kaspi-оплаты: сумма совпадает с бронированием, дата текущая, получатель корректный. Подтверждение или отклонение в течение 15 минут
- FR17: Гость может оплатить через платёжный агрегатор (PayBox/Wooppay)
- FR18: После подтверждения оплаты гость получает инструкцию (адрес, код замка/контакт хозяина, правила)
- FR19: Гость получает напоминание перед заездом
- FR20: Бронирование автоматически закрывается после выезда
- FR21: Гость может отменить бронирование (политика: бесплатно за 24ч, 50% за 12ч, без возврата <12ч)
- FR22: Хозяин может отменить бронирование с указанием причины, система уведомляет гостя
- FR23: Сбор за защиту взимается при каждом бронировании
- FR24: Гость может просмотреть историю своих бронирований

**Доступ к квартирам (FR25-FR28a):**
- FR25: Верифицированный гость получает код smart-замка (TTLock) после подтверждённой оплаты
- FR26: Код доступа генерируется на период бронирования (не постоянный)
- FR27: Для квартир без smart-замка доступна ручная передача ключей по согласованию с хозяином
- FR28: Система отслеживает статус smart-замка и уведомляет хозяина при проблемах (низкий заряд, офлайн)
- FR28a: Гарантия заселения: если гость не может получить доступ к квартире (код не работает, замок офлайн, хозяин не отвечает), система предлагает переселение в альтернативную квартиру в течение 15 минут или полный возврат оплаты

**Управление квартирами — Хозяин (FR29-FR42):**
- FR29: Хозяин может зарегистрироваться и добавить квартиры (фото, описание, цена, адрес, тип доступа)
- FR30: Хозяин может редактировать информацию о квартирах (цена, фото, описание)
- FR31: Хозяин может менять статус квартиры (доступна/недоступна)
- FR32: Занятость квартир синхронизируется с Google Calendar
- FR33: Система автоматически обновляет доступность квартиры при изменении в Google Calendar
- FR34: Хозяин видит доход по каждой квартире
- FR35: Хозяин видит статистику заполняемости своих квартир
- FR36: Хозяин может выгрузить финансовую отчётность за период (месяц, квартал)
- FR37: Хозяин получает уведомления о новых бронированиях
- FR38: Хозяин получает уведомление о новых отзывах на свои квартиры (с возможностью отключить)
- FR39: Хозяин получает автоматическую выплату после выезда гостя (минус комиссия платформы)
- FR40: Хозяин получает уведомление о выплате с детализацией (сумма, комиссия, итого)
- FR41: Хозяин загружает baseline-фото квартиры до заезда; гость подтверждает состояние при заезде; хозяин фиксирует состояние после выезда
- FR42: Хозяин может заблокировать конкретного гостя для своих квартир (персональный чёрный список)

**Верификация и рейтинги (FR43-FR50):**
- FR43: Пользователь подтверждает согласие на обработку ПД при регистрации
- FR44: Гость проходит верификацию (телефон + IIN) при первом бронировании
- FR45: Хозяин проходит верификацию (паспорт + документы на квартиру) при регистрации
- FR46: Квартира получает статус «Проверено» после верификации документов хозяина и проверки платформой; непроверенные квартиры отображаются с предупреждением «Не проверено — платформа не несёт ответственности»
- FR47: Гости и хозяева оценивают друг друга после бронирования (рейтинг + комментарий)
- FR48: Рейтинг гостя виден хозяевам внутри ЖильеGO
- FR49: Персональные данные гостя (IIN) скрыты от хозяина (виден только рейтинг и имя)
- FR50: Пользователь может запросить удаление своих персональных данных

**Коммуникация и поддержка (FR51-FR55):**
- FR51: FAQ-бот автоматически отвечает на вопросы из базы знаний (минимум 20 категорий: оплата, отмена, заезд/выезд, правила, smart-замок и др.). Цель автоматизации: 50% входящих обращений
- FR52: Гость может связаться с живым оператором
- FR53: Бот эскалирует нерешённые вопросы на живого менеджера
- FR53a: При запросе доп. услуг (трансфер, еда, уборка) бот сообщает «сервис в разработке» и предлагает ссылку на партнёрский сервис
- FR54: Система уведомляет гостя о статусе бронирования на всех этапах (подтверждение, напоминание, выезд)
- FR55: Система фиксирует инциденты и маршрутизирует их оператору

**Администрирование (FR56-FR62):**
- FR56: Админ видит дашборд со статистикой (бронирования, доход, конверсия, жалобы, рост, заполняемость)
- FR57: Админ может просматривать журнал действий с фильтрацией (по типу события, пользователю, дате)
- FR58: Админ может модерировать отзывы и жалобы
- FR59: Админ может заблокировать/разблокировать пользователя (гостя или хозяина)
- FR60: Админ может присвоить/изменить статус проверки квартиры
- FR60a: Админ может просматривать финансовую аналитику по городам и районам (доход, заполняемость, топ квартир)

**Landing и привлечение (FR61-FR62):**
- FR61: Посетитель видит landing page с описанием продукта и преимуществ
- FR62: Landing содержит QR-код для перехода в Telegram-бот

**Phase 2 Capabilities (FR63-FR74):**

- FR64: [Phase 2] Корпоративный заказчик может привязать контакт проживающего к каждой квартире

- FR66: [Phase 2] Корпоративный заказчик получает общий счёт для бухгалтерии
- FR67: [Phase 2] Агентство может зарегистрировать компанию и создать профили риелторов

### NonFunctional Requirements

**Performance (NFR-P1–P9):**
- NFR-P1: Время ответа Telegram-бота на пользовательский запрос: ≤2 сек (MVP), ≤1 сек (12 мес)
- NFR-P2: NLP-обработка запроса (intent extraction + entity recognition): <3 сек
- NFR-P3: Система поддерживает до 1000 одновременных активных пользователей бота (MVP). При 1000 concurrent users p95 latency ≤3 сек
- NFR-P4: Выплата хозяину — SLA: 99% выплат в течение 24 часов после выезда гостя, 100% — в течение 48 часов
- NFR-P5: Booking hold (блокировка квартиры при оплате) устанавливается за <1 сек
- NFR-P6: Web Performance (Landing): LCP <2.5s, FID <100ms, CLS <0.1, TTI <3s, bundle <200KB gzip
- NFR-P7: Web Performance (Admin SPA): LCP <3s, FID <100ms, CLS <0.25, TTI <4s, bundle <500KB gzip
- NFR-P8: WebSocket reconnect (Admin): <2 сек
- NFR-P9: Image pipeline: загрузка хозяином → resize завершается за 15 сек, доступность изображения — до 30 сек

**Security (NFR-S1–S9):**
- NFR-S1: Все данные передаются по HTTPS/TLS
- NFR-S2: IIN и паспортные данные хранятся в зашифрованном виде (encryption at rest)
- NFR-S3: Данные хранятся на серверах в Казахстане (Закон РК «О персональных данных и их защите»)
- NFR-S4: RBAC на уровне данных — субадмины-модераторы не имеют доступа к IIN и паспортным данным
- NFR-S5: Коды smart-замков передаются только верифицированным гостям, генерируются на период бронирования
- NFR-S6: Бэкапы — MVP: RPO ≤1 час, RTO ≤4 часа. Phase 2: RPO ≤15 минут, RTO ≤1 час
- NFR-S7: Rate limiting — многоуровневый (user-level, IP-level, action-based, global kill-switch)
- NFR-S8: Action-based лимиты: Поиск 10/мин, Бронирование 3/10 мин, Попытки оплаты 3/30 мин, Загрузка скринов 5/10 мин, Отзывы 2/сутки, Жалобы 3/сутки
- NFR-S9: Право на удаление персональных данных по запросу пользователя

**Scalability (NFR-SC1–SC5):**
- NFR-SC1: Система масштабируется от 200 до 1000 квартир; p95 latency не увеличивается более чем на 20%
- NFR-SC2: Архитектура поддерживает горизонтальное масштабирование сервисов (бот, API, воркеры)
- NFR-SC3: Единая инфраструктура для мультигородского расширения (Астана → Алматы → Шымкент)
- NFR-SC4: MVP: система выдерживает 3x рост трафика с деградацией <10%. Phase 2: 10x
- NFR-SC5: Uptime: 99.5% в месяц (MVP), 99.9% в месяц (12 мес)

**Integration (NFR-I1–I4):**
- NFR-I1: TTLock API — отказоустойчивость 4 уровня (retry → очередь → soft-fallback → hard-fallback). SLA: failure rate <5% за час
- NFR-I2: Google Calendar API — синхронизация ≤15 мин, критический порог >30 мин → защитный режим
- NFR-I3: Платёжные API (PayBox/Wooppay/Kaspi) — мультибанковая архитектура с автоматическим переключением при сбое основного провайдера
- NFR-I4: Telegram Bot API — webhook-архитектура с retry при ошибках доставки

**Monitoring & Observability (NFR-M1–M3):**
- NFR-M1: Мониторинг ключевых метрик: время ответа бота (p50/p95/p99), failure rate интеграций, количество активных бронирований, uptime
- NFR-M2: Автоматические алерты при превышении пороговых значений NFR-метрик
- NFR-M3: Логирование всех ошибок интеграций с достаточным контекстом для диагностики

### Additional Requirements

**Из Архитектуры:**
- Starter Template: full-stack-fastapi-template (tiangolo) — проект уже инициализирован. Epic 1 Story 1 должен учитывать это
- Tech Stack: FastAPI (Python) + PostgreSQL + Redis + aiogram 3 + Next.js/Vite (TypeScript)
- Async DB migration: asyncpg + AsyncSession — фундаментальное требование
- Redis обязателен с первого дня: sessions (TTL 30 мин), booking holds (10 мин), rate limiting, event queue (arq)
- NLP как модуль внутри API (не отдельный сервис) для solo-founder
- Shared code architecture: бизнес-логика в `shared/crud/`, routes/handlers — тонкие обёртки
- Bot ↔ API: direct DB access через shared CRUD (не HTTP)
- Event/Job dispatch: arq (Redis-backed) для background tasks
- Image upload: pre-signed URL → direct upload → arq worker → Pillow resize → CDN URL
- Docker Compose production: traefik, api, bot, workers, db, redis, frontend
- Deployment: git push main → GitHub Actions CI → SSH deploy to KZ VPS
- Infrastructure cost ≤$100/мес на MVP
- Серверы в Казахстане (compliance)
- Solo-Founder Constraint: ≤30 мин/день на operations, single-command deploy
- Unified auth: Telegram ID (bot), initData HMAC (Mini App), JWT (Admin SPA)
- Role model: `is_host: bool` flag + `is_superuser: bool` (не enum на MVP)
- Dual-layout frontend: Admin SPA (`/_layout/`) + Mini App (`/_miniapp/`)
- Data retention: booking history 3 года, chat 1 год, screenshots 90 дней, sessions 30 мин TTL
- Forward-only DB migrations (нет downgrade в production)
- Testing: pytest ≥80% shared CRUD, Playwright E2E 6 critical paths, aiogram.testing для бота

**Из UX Design:**
- Conversational-First UX: NLP текстовый поиск + aggressive fallback на кнопки
- Правило 3 кнопок (MAX_INLINE_BUTTONS = 3) — жёсткое UX-ограничение
- State-aware NLP: бот понимает контекст текущего state (критический prerequisite до запуска)
- Guided first experience: интерактивный туториал первого бронирования
- Welcome = демо-поиск с реальными результатами
- Карточки по одной (Yandex Go стиль): best match first, лимит 5 в боте, далее → Mini App
- Kaspi-оплата с прогресс-баром: "✓ Скриншот получен → ⏳ Проверяем → ✓ Подтверждено!"
- Auto-approve скриншота при совпадении суммы ±5% (критический prerequisite до запуска)
- Таймер эскалации: 5 мин нет ответа на скриншот → auto-approve + пометка "проверить позже"
- Hold автопродлевается после отправки скриншота (решает противоречие hold 10 мин < верификация 15 мин)
- Emoji-отзыв: 3 аспекта (чистота, заселение, фото) вместо одного общего рейтинга
- Smart-замок как бейдж "⚡ Мгновенный доступ" + приоритет в выдаче + ночной фильтр
- Умное ослабление фильтров при 0 результатов (никогда не показывать 0 результатов)
- Seed inventory: минимум 20 квартир в каждом популярном районе до запуска
- Design System: shadcn/ui + Tailwind CSS
- Brand Primary: #00b7c9 (teal)
- Dark mode: CSS variable switching, Telegram WebApp.colorScheme detection
- Mini App: Card Stack layout + Airy White карточка, bottom navigation (3 таба: Главная/Поиск/Профиль)
- Performance budget Mini App: max 200KB JS gzipped
- Tone of Voice: дружеский ("ты", не "вы"), бот = "умный друг"
- NLP-роутинг по роли: "Хочу снять" vs "Хочу сдать" → запоминает роль
- Хозяин: гибридная модель — быстрые операции через бот (NLP), тяжёлые через Mini App
- Онбординг хозяина: 5 шагов в Mini App (фото → основное → удобства → цена/доступ → превью), quality score
- Утренний дайджест для хозяев с категоризацией уведомлений (💰📅⭐🚨)
- Graceful degradation: decision trees для каждого failure mode
- 3 слоя памяти бота: Session Context (Redis 30 мин), Conversation History (PostgreSQL), User Profile (Phase 2)
- Skeleton screens вместо спиннеров для loading states
- Framer Motion для анимаций состояний, use-gesture для touch-жестов

**Из Brainstorming (MVP-приоритеты):**
