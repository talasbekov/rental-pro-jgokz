# Product Requirements Document - rental-pro-jgokz

**Author:** Erda
**Date:** 2026-02-04
**Version:** 0.6.0 (post-validation fixes)

## Executive Summary

**ЖильеGO** — Telegram-native маркетплейс посуточной аренды квартир в Казахстане. Гость описывает потребность на естественном языке, бот подбирает квартиру, принимает оплату и выдаёт код smart-замка — без звонков, без встреч, без скачивания приложения.

**Целевые пользователи:** командировочные (основной сегмент MVP), хозяева квартир, администратор платформы. Post-MVP: корпоративные заказчики, агентства недвижимости.

**Ключевые дифференциаторы:**
- **Conversational-First UX** — NLP-поиск вместо форм и фильтров. Ни один конкурент в КЗ этого не делает
- **On-Demand Mode** — квартира за 15 минут ночью (Uber-модель для аренды): smart-замок + геолокация + мгновенная оплата
- **Telegram-Native** — полноценный двусторонний маркетплейс внутри мессенджера, где уже есть пользователь

**География запуска:** Астана. Расширение: Алматы, Шымкент (12 мес).

**Бизнес-модель:** 10% комиссия с каждого бронирования + сбор за защиту (500–1500 ₸).

## Success Criteria

### Успех пользователей (User Success)

**Гость — aha-момент:** Беспроблемное заселение в запланированное время без единого звонка. Гость получает код доступа через бота в течение 5 минут после оплаты и заезжает самостоятельно.

- Successful Check-in Rate: ≥95% (MVP), ≥98% (12 мес)
- Время от выбора квартиры до оплаты: ≤1 мин
- Время ответа бота: ≤2 сек (MVP), ≤1 сек (12 мес)
- Retention (повторные бронирования): 25% за 90 дней (MVP), 35% за 12 мес — измеряется через привязанный аккаунт с историей, избранными квартирами и верификацией
- NPS: 50+ (MVP), 60+ (12 мес)

**Хозяин — aha-момент:** Хозяин ночью не встаёт из-за звонков. Гость приехал, сам заселился, сам выехал, деньги быстро пришли на счёт.

- Host Payout Success: 100%
- Доход хозяина: ≥100К ₸/мес (MVP), ≥150К ₸/мес (12 мес)
- Damage-free Rate: ≥98% (MVP), ≥99% (12 мес)
- Churn хозяев: <15%/год (MVP), <10%/год (12 мес)
- Заполняемость квартир: 50% мин / 65% цель (MVP), 70% (12 мес)

### Бизнес-успех (Business Success)

**3 месяца:**
- 1000 квартир в Астане (optimistic); Go-порог: 200-300 активных квартир
- 3-5 млн ₸ чистыми/мес (optimistic); break-even: 200 бронирований/мес при чеке 12К ₸
- Конверсия воронки (запрос → оплата): ≥40%

**12 месяцев:**
- Астана работает автономно
- Алматы: 1500+ квартир
- Выход в Шымкент
- 20-30 млн ₸ чистыми/мес

**Go/Pivot триггеры:**

| Критерий | Порог "Go" | Порог "Pivot" | Срок |
|----------|------------|---------------|------|
| Квартиры | 200+ активных | <30 | 8 недель |
| Бронирования | 300+/мес | <50/мес | 12 недель |
| Заполняемость | >15% | <10% | 12 недель |
| Retention гостей | >20% повторных | <10% | 12 недель |
| Unit Economics | Profit >0 | Убыток после 8 нед | 8 недель |
| Churn хозяев | <20%/мес | >40% уходят | 8 недель |

### Технический успех (Technical Success)

- Автоматизация бронирований без участия человека: ≥85% (MVP), ≥95% (12 мес)
- NLP intent recognition accuracy: ≥70% (MVP), ≥85% (12 мес)
- NLP fallback rate (переход на кнопочное меню): ≤30% (MVP), ≤15% (12 мес)
- Uptime: 99.5% в месяц (MVP), 99.9% в месяц (12 мес) — см. NFR-SC5
- Cost per Booking: ≤1000 ₸ (MVP), ≤500 ₸ (12 мес)
- Incident Rate (на 1000 бронирований): <1 (MVP), <0.5 (12 мес)
- Время founder на поддержку: <2ч/день; триггер эскалации: >4ч/день

### Измеримые результаты (Measurable Outcomes)

- Profit per Booking: ≥200 ₸ (MVP), ≥400 ₸ (12 мес)
- CAC (стоимость привлечения гостя): ≤1000 ₸ (MVP), ≤700 ₸ (12 мес)
- Net Host Growth: >50/мес (MVP), >100/мес (12 мес)
- Активация хозяев (Time to First Booking): ≤7 дней (MVP), ≤5 дней (12 мес)

## Product Scope & Phased Development

### MVP Strategy & Philosophy

**MVP-подход:** Problem-Solving MVP — минимальный продукт, решающий конкретную боль: «найти и заселиться в квартиру без звонков и встреч».

**Ключевой принцип:** Всё, что можно делать вручную на старте — делаем вручную. Автоматизируем только то, без чего продукт не работает.

**Платформа:** Telegram-бот (только Telegram на старте)
**География:** Астана — выбрана как первый город по трём причинам: (1) крупнейший командировочный трафик в РК (столица, госструктуры, Expo-инфраструктура), (2) высокая концентрация посуточной аренды в компактных районах (Есиль, Алматы), (3) Erda локально для личного онбординга первых хозяев
**Сегмент:** Командировочные (50% целевой доли)

**Ресурсы MVP:**
- Erda (founder) — продукт, операции, поддержка
- Юрист — оферта, договоры, compliance
- Бухгалтер — финансовая модель, налоги
- Сотрудники обзвона — онбординг хозяев, реклама продукта
- Разработка — аутсорс или найм (решение на этапе архитектуры)

### MVP Feature Set (Phase 1)

**Структура MVP: ядро + параллельные workstreams**

#### Ядро (блокирует запуск):
- Telegram-бот для гостей: NLP-поиск + aggressive fallback на кнопки при непонимании
- Telegram-бот/панель для хозяев: добавление квартир, уведомления, управление статусом
- Оплата: Kaspi-перевод (ручная верификация)
- Ручная передача ключей (fallback для квартир без smart-замка)
- Верификация: телефон + IIN (гости), паспорт + документы (хозяева)
- Сбор за защиту (500-1500₸)
- Базовая система отзывов (1-5 звёзд + комментарий)
- Landing-визитка (Tilda/Framer, не кастомный Next.js) + QR-код → Telegram-бот
- Базовый admin дашборд (бронирования, доход, жалобы) + журнал действий
- FAQ-бот (50% автоматизация) + живой оператор 09:00-23:00

#### Параллельные workstreams (не блокируют запуск, подключаются по готовности):
- TTLock интеграция → on-demand mode включается сразу после готовности
- PayBox/Wooppay → автоматическая оплата заменяет Kaspi-перевод
- Google Calendar sync для хозяев
- Image resize на сервере (простой resize, без полного pipeline)

**Core Journeys:**

| Journey | Scope | Комментарий |
|---------|-------|-------------|
| Гость (плановый + экстренный) | MVP | NLP с fallback на кнопки, оба mode (on-demand — после TTLock) |

- Первые 15 хозяев онбожены лично
- Резервный фонд 200К ₸

### Risk Mitigation Strategy

**Технические риски:**

| Риск | Митигация |
|------|-----------|
| NLP не достигает нужного качества | Aggressive fallback на structured flow (кнопки). NLP улучшается итеративно на реальных данных |
| TTLock интеграция нестабильна | Ручная передача ключей как полноценный fallback-flow. On-demand mode включается после стабилизации |
| Kaspi-скриншоты масштабируются плохо | Чёткий триггер переключения: >1ч/день или >30 бронирований/день → агрегатор |
| Фейковый скриншот Kaspi-оплаты | Временная мера → приоритетный переход на агрегатор с автоматическим подтверждением |
| 8 интеграционных точек для solo-founder | Разделение на ядро (блокирует запуск) и параллельные workstreams (подключаются по готовности) |
| Двойное бронирование (race condition) | Booking hold — блокировка квартиры на 10 минут при начале оплаты |
| Сбой платёжной системы | Мультибанковая архитектура (Kaspi + Halyk + агрегатор) |
| Утечка персональных данных | Серверы в КЗ + шифрование + RBAC на уровне данных + минимизация доступа |

**Рыночные риски:**

| Риск | Митигация |
|------|-----------|
| Хозяева не хотят ставить smart-замки | Оба mode работают: smart-замок + ручная передача. Ночной mode стимулирует переход |
| Мало квартир на старте | Сотрудники обзвона + личный онбординг первых 15 хозяев. Go-порог: 200 квартир |
| Krisha.kz запустит посуточную аренду | Защита: NLP UX + on-demand mode + Telegram-native — технологические барьеры, которые классифайд не повторит быстро. Switching cost: рейтинг гостя работает только в ЖильеGO. Network effects: чем больше квартир с smart-замками — тем сильнее on-demand mode |
| Командировочные не знают про бота | Landing-визитка с QR-кодом + таргетированная реклама + партнёрства с компаниями |
| Мошенничество с объявлениями (фейковые фото) | Верификация хозяев + документы на квартиру + отзывы |
| Неоплата / отмена в последний момент | Политика отмены: бесплатно за 24ч, 50% за 12ч, без возврата <12ч |
| Ущерб квартире | Сбор за защиту + резервный фонд 200К₸ + baseline фото |

**Ресурсные риски:**

| Риск | Митигация |
|------|-----------|
| Меньше ресурсов, чем планировалось | Запуск только с ядром: 50 квартир, Kaspi-only, ручная передача. Workstreams — по мере ресурсов |
| Erda перегружен операциями | Триггер эскалации: >4ч/день на поддержку → нанять оператора |

## User Journeys

### Journey 1: Гость — поиск и бронирование квартиры [MVP]

**Персона:** Ердаулет, 32 года, менеджер по продажам.

**Два mode использования:**

#### Mode A: Плановое бронирование

**Opening Scene:** Ердаулет летит из Алматы в Астану на деловую встречу. Заранее ищет квартиру.

**Rising Action:** Открывает Telegram-бота ЖильеGO. Пишет:

> «Меня зовут Ердаулет, с 10 по 13 февраля хочу снять квартиру возле Байтерека в Астане. Бюджет примерно 15000₸ за ночь, желательно 2-комнатную. Со мной будет ещё один человек. Прилечу из Алматы в 18:00, хочу заселиться к 19:30.»

Бот анализирует запрос (NLP), извлекает параметры. Если чего-то не хватает — уточняет. Предлагает отправить геолокацию или указать ориентир для сортировки по расстоянию. Выдаёт только свободные на запрашиваемые даты квартиры — карточки с фото, описанием, рейтингом, ценой, расстоянием. Ердаулет листает кнопкой «Следующий».

Выбирает квартиру → бронирует → оплачивает через Kaspi (копирует реквизиты, загружает скрин). Бот подтверждает и выдаёт инструкцию: адрес, код замка, правила.

Ердаулет хочет трансфер из аэропорта — пишет боту. Бот сообщает, что сервис доп. услуг в разработке, и предлагает ссылку на партнёрский сервис трансфера. Если бот не может решить вопрос — связывает с живым менеджером.

**Climax:** В день заезда — напоминание с адресом и кодом. Ердаулет приезжает, вводит код, заходит — всё как на фото.

**Resolution:** После выезда — оценка (1-5 звёзд + комментарий). Рейтинг Ердаулета растёт. Квартира в избранном. Следующая командировка — бронирование за 2 минуты.

#### Mode B: Экстренное бронирование (ночной сценарий)

**Opening Scene:** Аслан, 27 лет, вышел из клуба в 2 ночи. Нужна квартира прямо сейчас, рядом.

**Rising Action:** Открывает бота, пишет:

> «Хочу быстро снять квартиру рядом, бюджет 15000₸, заехать через 20 минут»

Бот запрашивает геолокацию. Фильтрует: только мгновенный доступ (smart-замок/бокс), в радиусе 2-3 км, свободные прямо сейчас. Выдаёт ближайшие варианты.

**Climax:** Аслан выбирает → бронирует → оплачивает. Приоритет: интеграция с платёжным агрегатором для оплаты в 1 клик (Kaspi-копирование — fallback). Через 2 минуты — адрес и код. Заезжает через 15 минут. Никому не звонил.

Хочет заказать еду — пишет боту. Бот сообщает, что сервис доп. услуг в разработке, и предлагает ссылку на партнёрскую доставку. Если бот не справляется — эскалация на менеджера.

**Resolution:** Утром автозакрытие бронирования. Запрос на оценку. Хозяин видит выплату.

**Раскрытые требования:**
- NLP-обработка запроса с извлечением параметров → FR1, FR2, FR3
- Уточняющие вопросы бота при нехватке данных → FR3
- Геолокация гостя для сортировки по расстоянию → FR4
- Real-time проверка availability → FR5
- Карточки квартир с последовательным просмотром → FR6, FR7, FR12
- Structured flow как альтернатива NLP → FR8
- Фильтр «доступно прямо сейчас» + мгновенный доступ ночью → FR10
- Оплата: Kaspi (копирование + скрин) + платёжный агрегатор → FR15, FR16, FR17
- Автоматическая выдача инструкции после оплаты → FR18
- Напоминание перед заездом → FR19
- Гарантия заселения: переселение за 15 мин или возврат → FR28a
- Доп. услуги: бот сообщает «сервис в разработке» и предлагает ссылку на партнёра → FR53a
- Эскалация на живого менеджера → FR53
- Система отзывов и рейтинга гостя → FR47, FR48
- Избранные квартиры в аккаунте → FR11
- Автозакрытие бронирования при выезде → FR20

### Journey 2: Айнура — хозяйка квартир [MVP]

**Персона:** Айнура, 45 лет, владеет 3 квартирами в Астане. Устала от ночных звонков и ручной работы.

**Opening Scene:** Айнура тратит 3 часа в день на переписку, фото-проверки, передачу ключей. Хочет пассивный доход.

**Rising Action:** Регистрируется в боте как хозяин. Добавляет 3 квартиры: фото, описание, цена, адрес, тип доступа (smart-замок на двух, ручная передача на третьей). Видит доход по каждой квартире. Занятость квартир синхронизируется в Google Calendar. Может менять статус квартиры (доступна/недоступна), редактировать цену, обновлять фото и описание.

**Climax:** Ночью приходит уведомление: «Новое бронирование — Квартира №2, Ердаулет, 3 ночи, 45000₸». Айнура не просыпается — smart-замок выдал код автоматически. Утром видит: гость заселился, деньги на балансе.

В Google Calendar видит — квартира №1 свободна на выходных. Через бота меняет статус на «доступна» и поднимает цену.

**Resolution:** За месяц — 320К₸ с трёх квартир. 15 минут в день вместо 3 часов. Полная прозрачность дохода по каждой квартире.

**Раскрытые требования:**
- Регистрация хозяина с добавлением квартир → FR29
- Просмотр дохода по каждой квартире → FR34
- Интеграция с Google Calendar для календаря занятости → FR32, FR33
- Управление статусом квартиры (доступна/недоступна) → FR31
- Редактирование квартир (цена, фото, описание) → FR30
- Уведомления о бронированиях → FR37
- Автоматические выплаты → FR39, FR40
- Baseline-фото и контроль состояния → FR41
- Блокировка конкретного гостя → FR42

### Journey 3: «ТехноСервис» — корпоративное бронирование [Growth]

## Domain-Specific Requirements

### Платежи и финансы

**MVP:**
- Оплата через редирект на страницу банка (Kaspi, Halyk) или ввод карты
- Kaspi-перевод как **временная мера** (копирование реквизитов + загрузка скрина подтверждения + ручная верификация). Триггер переключения на агрегатор: >1ч/день на подтверждения ИЛИ >30 бронирований/день
- Booking hold: блокировка квартиры на 10 минут при начале оплаты для предотвращения двойного бронирования
- Выплата хозяину автоматически после выезда гостя (минус 10% комиссия) — SLA см. NFR-P4
- Сбор за защиту (500-1500₸) формирует резервный фонд
- Налоги платформы — из комиссии (10%); налоговые обязательства хозяев — на стороне хозяев
- Налоговый режим 2026: платформа работает как ИП или ТОО на упрощённой декларации. При росте оборота (>100М ₸/год) — переход на общеустановленный режим. Хозяевам рекомендуется ИП с патентом (3% от дохода) — платформа может предоставлять справки о доходах для налоговой отчётности хозяев

**Growth:**
- Прямая интеграция с Kaspi и другими банками
- Групповая оплата для корпоративных заказчиков
- Выставление счетов/чеков для бухгалтерии

### Персональные данные и приватность

- Хранение данных на серверах в Казахстане (Закон РК «О персональных данных и их защите»)
- Обязательное согласие пользователя на обработку ПД при регистрации
- Собираемые ПД: телефон, IIN (гости), паспортные данные и документы на квартиру (хозяева), геолокация (по запросу)
- IIN гостя виден хозяину только как имя и рейтинг — полные данные скрыты
- Измеримые требования к защите данных — см. NFR Security (NFR-S1–S9)

### Верификация

- Гости: номер телефона + IIN — верификация при первом бронировании, периодическая ревалидация
- Хозяева: паспорт + документы на квартиру (обязательно при регистрации)
- Рейтинговая система: гости и хозяева оценивают друг друга
- Рейтинг гостя работает только внутри ЖильеGO (switching cost)

### Безопасность и ответственность

- Платформа выступает как информационный посредник, содействует в разрешении конфликтов, но не несёт прямой ответственности за действия пользователей
- Юридическая оферта чётко разграничивает ответственность: платформа ↔ хозяин ↔ гость
- Коды доступа к smart-замкам передаются только верифицированным гостям после подтверждённой оплаты
- Коды генерируются на период бронирования (не постоянные)
- Протокол реагирования на инциденты: бот фиксирует → оператор в течение 15 мин → категоризация → решение или компенсация из фонда

## Innovation & Novel Patterns

### Detected Innovation Areas

**1. Conversational-First UX (vs Form-Based)**
Все конкуренты на рынке КЗ — классические сайты и приложения с фильтрами и формами. ЖильеGO строит принципиально другой UX: гость описывает ситуацию естественным языком, бот извлекает параметры и подбирает варианты. Это не чат-бот с кнопками — это полноценный conversational interface.

Расширение:
- Бот запоминает предпочтения и предлагает «как в прошлый раз»
- Понимание неявных потребностей из контекста
- Проактивные предложения на основе истории

**2. On-Demand Mode (квартира как такси)**
Ночной сценарий «квартира за 15 минут» — ближе к on-demand сервису (Uber-модель), чем к классическому бронированию. Ни один конкурент в КЗ этого не делает. Фильтр только по smart-замкам + геолокация + мгновенная оплата = уникальный продуктовый слой.

**3. Telegram-Native маркетплейс**
Полноценный двусторонний маркетплейс внутри Telegram с NLP, платежами, smart-замками и RBAC — нет аналогов в Казахстане. Конкуренты заставляют скачивать приложение или заходить на сайт. ЖильеGO живёт там, где уже есть пользователь.

### Validation Approach

| Инновация | Как валидировать | Метрика успеха |
|-----------|-----------------|----------------|
| Conversational UX | A/B: NLP-запрос vs кнопочное меню | Конверсия в бронирование, время до оплаты |
| On-Demand Mode | Трекинг ночных бронирований (22:00-06:00) | Доля ночных бронирований >10%, время от запроса до заезда <30 мин |
| Telegram-Native | Сравнение retention с web-конкурентами | Retention >25% vs средний по рынку ~15% |

### Innovation Risk Mitigation

| Риск | Fallback |
|------|----------|
| NLP не понимает запросы | Fallback на structured flow (кнопки + меню), постепенное обучение модели |
| Ночной mode не востребован | Фича остаётся, но не выделяется в отдельный продуктовый слой |
| Telegram ограничивает функционал | Mini App (WebApp внутри Telegram) для сложных сценариев |

## Non-Functional Requirements

### Performance

- **NFR-P1:** Время ответа Telegram-бота на пользовательский запрос: ≤2 сек (MVP), ≤1 сек (12 мес)
- **NFR-P2:** NLP-обработка запроса (intent extraction + entity recognition): <3 сек
- **NFR-P3:** Система поддерживает до 1000 одновременных активных пользователей бота (MVP). При 1000 concurrent users p95 latency ≤3 сек
- **NFR-P4:** Выплата хозяину — SLA: 99% выплат в течение 24 часов после выезда гостя, 100% — в течение 48 часов
- **NFR-P5:** Booking hold (блокировка квартиры при оплате) устанавливается за <1 сек
- **NFR-P6:** Web Performance (Landing): LCP <2.5s, FID <100ms, CLS <0.1, TTI <3s, bundle <200KB gzip
- **NFR-P7:** Web Performance (Admin SPA): LCP <3s, FID <100ms, CLS <0.25, TTI <4s, bundle <500KB gzip
- **NFR-P8:** WebSocket reconnect (Admin): <2 сек
- **NFR-P9:** Image pipeline: загрузка хозяином → resize завершается за 15 сек, доступность изображения — до 30 сек

### Security

- **NFR-S1:** Все данные передаются по HTTPS/TLS. Стандартный TLS достаточен для MVP
- **NFR-S2:** IIN и паспортные данные хранятся в зашифрованном виде (encryption at rest, индустриальный стандарт шифрования)
- **NFR-S3:** Данные хранятся на серверах в Казахстане (Закон РК «О персональных данных и их защите»)
- **NFR-S4:** RBAC на уровне данных — субадмины-модераторы не имеют доступа к IIN и паспортным данным
- **NFR-S5:** Коды smart-замков передаются только верифицированным гостям, генерируются на период бронирования
- **NFR-S6:** Бэкапы — MVP: RPO ≤1 час, RTO ≤4 часа. Phase 2: RPO ≤15 минут, RTO ≤1 час
- **NFR-S7:** Rate limiting — многоуровневый (user-level, IP-level, action-based, global kill-switch). Конкретные пороги по уровням user/IP/global определяются в архитектурном документе
- **NFR-S8:** Action-based лимиты (бизнес-правила):

| Действие | Лимит |
|----------|-------|
| Поиск квартир | 10/мин |
| Создание бронирования | 3/10 мин |
| Попытки оплаты | 3/30 мин |
| Загрузка скринов | 5/10 мин |
| Отзывы | 2/сутки |
| Жалобы | 3/сутки |

- **NFR-S9:** Право на удаление персональных данных по запросу пользователя

### Scalability

- **NFR-SC1:** Система масштабируется от 200 до 1000 квартир; p95 latency не увеличивается более чем на 20%
- **NFR-SC2:** Архитектура поддерживает горизонтальное масштабирование сервисов (бот, API, воркеры)
- **NFR-SC3:** Единая инфраструктура для мультигородского расширения (Астана → Алматы → Шымкент)
- **NFR-SC4:** MVP: система выдерживает 3x рост трафика с деградацией <10%. Phase 2: 10x
- **NFR-SC5:** Uptime: 99.5% в месяц (MVP), 99.9% в месяц (12 мес)

### Integration

- **NFR-I1:** TTLock API — отказоустойчивость 4 уровня:
  1. **Retry** с exponential backoff и таймаутом
  2. **Очередь** с идемпотентными повторами
  3. **Soft-fallback:** уведомление хозяину и гостю, логирование инцидента
  4. **Hard-fallback:** ручная передача ключей (крайний сценарий)
  - SLA: failure rate <5% за час; алерт в админку при превышении
  - Конкретные параметры retry/backoff/TTL определяются в архитектурном документе

- **NFR-I2:** Google Calendar API — синхронизация:
  - Допустимая задержка синхронизации: ≤15 мин
  - Критический порог: >30 мин → защитный режим (квартира помечается как «доступность уточняется» или временно недоступна)
  - Retry с backoff при ошибках API. Конкретный механизм синхронизации определяется в архитектурном документе

- **NFR-I3:** Платёжные API (PayBox/Wooppay/Kaspi) — мультибанковая архитектура с автоматическим переключением при сбое основного провайдера

- **NFR-I4:** Telegram Bot API — webhook-архитектура с retry при ошибках доставки, логирование недоставленных сообщений

### Monitoring & Observability

- **NFR-M1:** Система обеспечивает мониторинг ключевых метрик: время ответа бота (p50/p95/p99), failure rate интеграций (TTLock, Calendar, платежи), количество активных бронирований, uptime
- **NFR-M2:** Автоматические алерты при превышении пороговых значений NFR-метрик
- **NFR-M3:** Логирование всех ошибок интеграций с достаточным контекстом для диагностики

### Accessibility

Базовые требования a11y зафиксированы в секции «Web App Specific Requirements»: контрастность 4.5:1, клавиатурная навигация, alt-тексты, семантическая разметка, focus-индикаторы. Полный WCAG 2.1 AA не требуется.
